## Self-caught defect during build (the recurring pattern, found before review)
The first cut of the gate read the API server's host/key from `config["platforms"]["api_server"]`. Verified against the runtime: **`load_config()` returns `platforms: None`** — the API server is configured from **env vars** (`API_SERVER_ENABLED` / `API_SERVER_KEY` / `API_SERVER_HOST`, assembled in `gateway/config.py:1534-1554`), not the config dict. So the first cut would have found nothing in production and **never blocked** — inert exactly like the prior three slices' defects, and the initial tests passed only because they hand-built a `platforms` block the merged config never carries. **Fixed:** `_network_listener_without_auth` now detects the API server from EITHER the config platforms block OR the real env trigger; the tests drive the **env** trigger (not an injected config), and the e2e verification blocks via env only. This one was caught in-build by checking the load-bearing assumption ("does the merged config actually carry this?") rather than waiting for review.

## Capability preservation
The gate is inert unless the posture is strict AND the relevant `require_*` switch is on. It only blocks a **network-exposed, unauthenticated** control plane — the intended fail-closed RCE guard. A loopback-only single-operator CLI/gateway (the demo/eval boundary) is unaffected. No tool/skill/MCP/provider is removed.

## Independent review outcome (per-slice adversarial pass)
Both reviewers ran. The **P1 they'd have flagged (RCE gate inert on the env-var path) was already self-caught and fixed in-build** — the logic reviewer read the fixed tree and confirmed "the production-shape bug is NOT present … the control is live in production." Useful context from the security reviewer: the pre-existing `APIServerAdapter.connect()` guard is the real RCE trust boundary (it refuses a network bind without a ≥16-char key); this P1.5 gate is the **governed, audited, fail-closed-at-startup** layer over it. Additional findings, all fixed in-slice:
- **P2 (security) — switches weren't strict-coerced.** An agent could set `api_server_key_required: false` in home config while staying strict, demoting the gate to advisory. **Fixed:** added both switches to `posture_resolver._STRICT_COERCIONS` — strict now forces them true (verified: `False->True`).
- **P2 (security) — weak-but-nonempty key passed the gate.** A key of `"x"` slipped it. **Fixed:** the gate now uses `has_usable_secret(key, min_length=16)`, parity with the adapter's entropy floor; a weak key blocks.
- **P2 (logic) — enablement predicate too broad.** A stray `API_SERVER_HOST` (or `"on"`) triggered a spurious fail-closed over-block for a server the gateway never starts. **Fixed:** the predicate now mirrors `gateway/config.py:1539` exactly (`enabled ∈ {true,1,yes}` OR key set); regression test for host-alone.
- **P3 (logic) — blocking findings weren't logged when non-strict.** **Fixed:** they now log as advisory so a keyless endpoint is never operator-invisible.
- **P3 (accepted residual) — TLS env-only check** misses a per-endpoint MCP `ssl_verify: false` (LG-IA-08-R1) and `_effective_is_strict` swallows errors (consistent with the P1.3 gate) — recorded for the remediation pass.
