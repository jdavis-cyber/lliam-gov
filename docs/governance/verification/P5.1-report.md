## Design — fail-safe hook at the sealed-record seam
The hub is a process singleton (`governance_audit.get_monitor_hub`) built from
the merged `monitoring` config; `_feed_monitors(record)` runs after the ledger
append+fsync and **never raises into the emit path** (a monitor or sink failure
cannot break the tamper-evident write). Complete no-op when `monitoring` is
absent (`MonitorHub.enabled == False`, `build_sink → None`) — the low side is
untouched. Enforcement is at the runtime seam every event flows through (the
ledger emit), not a startup snapshot: env-supplied hosts, mid-session provider
switches, MoA/auxiliary/delegation calls all seal a record and are observed.

## What was tested (the AI-499 VERIFY criteria)
1. **Events reach the SIEM sink (LG-MO-05):** the sink writes JSON lines with
   `event`, `ts_ingest`, and `source`; disabled/absent config → `build_sink`
   returns None (no-op); `forward` never raises on a bad path.
2. **Injected egress anomaly raises an alert (LG-MO-02):** after a known
   baseline host, a first-seen egress host on a `web_fetch` dispatch fires
   `LG-MO-02`; an egress count past the threshold fires a volume-spike alert.
3. **Injected runaway loop raises an alert (LG-MO-01):** N consecutive
   identical tool dispatches past `runaway_threshold` fire `LG-MO-01`; varied
   activity does not (no false positive).
4. **Drift (LG-MO-03):** a changed MCP tools-hash/scope-set fires; an identical
   signature does not.
5. **Session timeline + notification (LG-MO-06):** two alerts in one session
   correlate into a timeline; a notification to the configured named staff is
   queued and also streamed to the sink.
6. **Capability preservation:** a hub with no `monitoring` config is a complete
   no-op; the real overlay `monitoring` block builds a live sink + hub.
7. **Live wiring:** `governance_audit.emit` contains the `_feed_monitors` hook.
