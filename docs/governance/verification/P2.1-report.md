## Objective
Build the graduated authorization engine at the dispatch chokepoint: a per-call
PDP (`tools/tool_policy.py` — ADDITIVE extension of the P0 enablement gate)
that resolves every tool call to exactly one of the four dispositions
(allow / detect_log / hitl_approve / deny) from `policy/tool-risk-policy.yaml`,
with privileged-function force-up, zero-standing-privilege JIT grants,
per-turn/per-session mutating-call budgets, and fail-closed defaults — wired at
the same seams the P1.2 audit gate uses (both `tool_executor` dispatch paths +
the `model_tools.handle_function_call` direct funnel), evaluated **exactly once
per call**.

## What was tested
1. **LG-RM-08 four-tier ladder** — one call per tier against the REAL backends
   (`agent/file_safety.py` write split, `tools/approval.py` shell guards):
   `file_read`→allow; in-safe-root write→detect_log (proceeds, NO prompt);
   outside-safe-root write→hitl_approve (gated); sensitive path (`~/.ssh/…`),
   hardline shell (`rm -rf /`), sudo-stdin, computer_use→deny.
2. **Deny-by-default + fail-closed** — unmatched class → `default_disposition`
   (deny); unparseable policy file → every call denied (`fail_closed`); PDP
   internal error → fail-closed block (`pdp_error`).
3. **Capability preservation** — low-side posture is a COMPLETE no-op (allow,
   PDP inactive); every resolvable call lands on an explicit policy class
   (memory_write, skill_write, delegation, network.egress,
   tool_mutation.bounded — incl. unknown/MCP tools) so strict posture adds no
   blanket-deny of legitimate capability; `hitl_delegated_to_backend: true`
   classes (shell.destructive → existing `tools/approval.py` flow;
   memory/skill writes → existing `write_approval` staging) are NOT
   double-blocked by the PDP.
4. **LG-AZ-06 privileged force-up** — a privileged member never resolves below
   hitl_approve even when its class tier is lower.
5. **LG-AZ-07 ZSP/JIT** — default-off capability without a grant → hitl;
   active grant → proceeds with full record; expired grant → re-approval;
   a grant NEVER re-enables a deny class (deny is terminal).
6. **LG-AZ-10/12 budgets** — 4th mutating call over a per-turn cap of 3 →
   hitl_approve ("pausing for approval", not a hard halt); reads consume no
   budget; new turn resets per-turn but the per-session cap still trips.
7. **LG-AZ-01 chokepoint wiring** — PDP-denied call through the public
   `handle_function_call` funnel is blocked BEFORE `registry.dispatch`;
   executor-gated path (`skip_governance_predispatch=True`) is not re-gated
   (exactly-once — budget counters cannot double-consume); both executor
   seams invoke `pdp_gate` + per-turn reset (source-verified).
8. **Ledger accountability** — a blocking PDP verdict emits `policy.violation`
   to the hash-chained ledger with action class, disposition, origin, reason.
9. **LG-RM-03 coverage reconciliation** — every class the resolver can produce
   has an explicit tier in the policy of record (test-enforced, cannot drift).

## Expected-deny cases (by design)
- Hardline shell / sudo-stdin / sensitive-path writes / computer_use /
  browser actions / package_install / non-allowlisted provider — deny is
  terminal; no toggle, JIT grant, or privileged mapping re-enables it.
- `hitl_approve` verdicts not delegated to an existing backend gate block
  fail-closed pending an authenticated approver (`deny_on_no_approver`,
  LG-HO-06 scoped to the High tier). P2.2 (AI-482) binds these to the real
  approval gates.
