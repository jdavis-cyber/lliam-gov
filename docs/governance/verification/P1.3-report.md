## Objective
Add tamper-evidence verification for the ledger: a `verify_chain()` routine that walks the JSONL and validates every `prev_hash` + `record_hash` link, run at startup (fail-closed/alert on a break) and as a new CI/cron gate that fails on any break.

## What was built (all additive — no existing path renamed)
- **`agent/governance_audit.py` — `verify_chain()`** + `ChainVerificationResult`. Walks the ledger, recomputes each `record_hash` from canonical bytes, checks each `prev_hash` links to the prior record, and checks `seq` is contiguous. Reports the FIRST break (`break_seq` + `reason`). A missing/empty ledger is PASS (`total=0`). Optional `start_after_seq` / `start_prev_hash` segment verification (spec §4.3 — O(segment) once anchoring exists).
- **`lliam_cli/security_audit_startup.py` — `verify_audit_chain_at_startup()`** + `AuditChainVerificationError` (additive functions in the existing startup-audit module). No-op when the ledger is disabled; PASS logs at debug; a break always logs `critical` and appends a `security.error` alert to the ledger; under strict posture with `audit.verify_fail_action: block` it RAISES (refuse to rely on a tampered ledger, spec §4.3), otherwise alert-only. Idempotent per process.
- **`gateway/run.py`** — calls `verify_audit_chain_at_startup` right after the existing `log_startup_security_warnings`; the fail-closed exception propagates (unlike the advisory posture warnings, which are swallowed).
- **`ci/governance-ci-gates/audit_chain_gate.py`** (NEW) — the standing detective control: exit 1 on any break, 0 on a clean/absent ledger, 2 on error; `--ledger` and `--require-strict` flags. Runs both as a CI job and as the host cron job.
- **`ci/governance-ci-gates/audit_chain_selftest.py`** (NEW) — CI self-test exercising the real verifier from a bare checkout (PASS on good, FAIL on tamper) so the CI gate has teeth even without a production ledger.
- **`.github/workflows/governance-gates.yml`** — new `audit-chain` job (self-test + gate) feeding `all-checks-pass`; added a daily `schedule` (cron `17 7 * * *`) as the LG-AU-08 scheduled detective control.
- **`cli-config.gov.yaml`** — `[ACTIVE @ P1.3]` keys `verify_on_startup: true`, `verify_fail_action: block`.

## What was tested
1. `verify_chain` PASS on a good ledger (5 records); missing/empty ledgers PASS with `total=0`.
2. Break detection: in-place edit → `record_hash mismatch` at the edited seq; deletion → seq-gap break; reorder → break. First break reported.
3. Segment verification after an anchor seq (checks only the forward segment).
4. Startup hook: no-op when disabled; PASS on good; **RAISES** `AuditChainVerificationError` under strict+block on tamper; **alert-only** (no raise) under advisory posture; skipped when `verify_on_startup: false`; idempotent per process.
5. CI scripts: self-test PASS/FAIL both correct; gate exits 1 on a real tampered ledger, 0 on an absent one.
6. Regression: existing `test_security_audit_startup.py` unaffected by the additive functions.

## Expected-deny / expected-block cases
- Tampered chain at gateway startup under strict posture → **startup blocked** (`AuditChainVerificationError`, LG-AU-08 fail-closed).
- Tampered chain in CI or host cron → **gate exit 1** (build/cron fails; tamper surfaced).
- Advisory (non-strict) posture on tamper → **alert-only**, startup proceeds (capability-preserving for low-side).

## Capability preservation
`verify_chain` is read-only. The startup hook and CI gate no-op when the ledger is disabled (shipped/low-side profile). The only blocking behavior is the intended LG-AU-08 refusal to rely on a **proven-tampered** ledger under strict posture — the correct fail-closed response for a CUI audit system. The cron/CI gate is additive and skips cleanly with no ledger present.

## Independent review + fixes (per-slice adversarial pass)
A local logic + security review of this diff ran before push. It found **one P1** (in both reviewers, independently) plus fail-open gaps — all fixed in this slice:

- **P1 — fail-closed startup block was dead in production.** The gateway passed `read_raw_config()` to the hook, but `security.posture: strict` (and the `audit:` block) exist only in the overlay-merged config, so `is_strict()` was always False and the block never fired; the green test hid it by hand-feeding a merged-shape dict. **Fixed:** the gateway now passes `load_config()`, AND the hook re-resolves posture + audit settings from the effective merged config (`_effective_is_strict` / `_effective_config`) so a raw-shaped config can't defeat it — and the agent can't neuter the gate by writing `verify_on_startup: false` into its home config (overlay wins the merge). Regression test drives the raw-config production shape.
- **P2 — verify fails open on a corrupt line.** `iter_records`' `json.loads` raised, and the hook swallowed it as "non-fatal" → no block. **Fixed:** `verify_chain` now uses a guarded iterator and returns `ok=False` ("unparseable ledger line") on a bad line — corruption is a break, never a shrug.
- **P2 — segment mode ignored `start_prev_hash`.** The trusted anchor was overwritten by the on-disk record's own claimed hash. **Fixed:** the anchor's seal is recomputed and must equal the caller-supplied `start_prev_hash`, else the anchor is reported as the break.
- **P2 — `_CHAIN_VERIFIED` latched before verifying.** **Fixed:** the sentinel is set only after a verification completes, so a skip/transient error doesn't permanently disable the control.
- **P2 — the "cron detective control" only self-tested in CI.** **Fixed:** committed `ci/governance-ci-gates/audit_chain_cron.sh` — the host cron unit that runs the gate against the real ledger with pinned `HERMES_HOME`/`HERMES_CONFIG` (fail-closed if unset) and an optional alert command. The CI schedule is now described as self-test only.

## Accepted residuals & operator runbook (LG-AU-08-R1)
- **Suffix-truncation / whole-file deletion is not detected by `verify_chain` alone** — an internal hash chain has no high-water mark, so a consistent prefix verifies as PASS. The standing detective control for this is **external anchoring + an external record count** (spec §4.2), deferred with the anchor work. Until then: the gate wording says "internally consistent" (not "complete/untampered"), and `checked`/`total` are returned so an external count can detect shrinkage.
- **Whole-chain rewrite from genesis, or a validly-sealed forged tail, passes `verify_chain`** — it proves internal consistency (tamper-evidence of in-place edits/reorders/deletions-within), NOT authenticity. Authenticity comes from per-record NPE-identity signing (P1.4) + external anchoring. This is the accepted P1.1 direct-`open()` residual.
- **Operator recovery from a fail-closed startup block:** a tampered ledger halts gateway startup by design. Recovery = investigate the reported `break_seq`, quarantine the current ledger for forensics, and either restore from the last externally-anchored good segment or rotate-and-reseal a fresh genesis ledger (documented sealed cut-over), then restart. Fail-closed is intentional — do NOT bypass by disabling `verify_on_startup`.

## Deferred to later steps (by design)
- External anchoring / WORM replication (spec §4.2) — hardens against a host-level rewrite/truncation; `start_after_seq`/`start_prev_hash` segment verification is in place to consume anchors when they exist.
- Real NPE `instance_id` in records + per-record identity signing → P1.4 (AI-519).
- Startup verify is wired at the gateway seam (the network-exposed surface, mirroring the existing `log_startup_security_warnings` wiring); CLI-only boots are covered by the CI + host-cron detective control. Confirm the in-scope §5.1 asset boots through the gateway, or add the CLI call site, at the P1.V gate.
